# План разработки «Мой университет»

Версия 1 · 24 октября 2026 · ждёт утверждения

Опирается на [методологию расписания](methodology.md). Порядок: сначала логика, потом дизайн.

## Принципы разработки

- **Сначала логика, потом дизайн.** Логику проверяем автоматическими тестами и простым техническим интерфейсом, дизайн кладём поверх уже проверенной логики.
- **Движок расписания — отдельный модуль** без базы, без интернета и без интерфейса. Его можно прогнать на любом сценарии за секунды.
- **Одна проверка правил на всех.** Любое изменение расписания — алгоритм, перенос, перетаскивание руками, правка в Google — проходит через один и тот же «проверяльщик правил». Так правила не разъедутся в разных местах.
- **Одна очередь вопросов.** Всё, о чём сервис тебя спрашивает (конфликты, пропуски, калибровка, контрольные точки), попадает в единый раздел «Решения».
- **Всё на твоём ПК.** Наружу уходит только обмен с Google Календарём.

## Технологии

| Часть | Выбор | Почему |
|---|---|---|
| Язык | TypeScript везде | один язык для движка, сервера и интерфейса; типы ловят ошибки в сложной логике |
| Движок | чистый модуль TypeScript + тесты на Vitest | быстрые тесты сценариев |
| Сервер | Node.js + Fastify | лёгкий, работает локально |
| База | SQLite (один файл) + Drizzle ORM | не нужен отдельный сервер БД, резервная копия — просто копия файла |
| Даты и время | Luxon | надёжная работа с часовыми поясами и неделями |
| Google | официальная библиотека `googleapis` | вход и Calendar API |
| Интерфейс | React + Vite, на этапе дизайна — Tailwind CSS | |
| Звук | Web Audio API, записи со свободной лицензией | смешивание и громкость без сторонних сервисов |
| Версии | git | история изменений, откат при ошибке |

На ПК уже есть Node.js 24, npm 11 и git 2.55 — ставить ничего не нужно.

**Структура проекта:**

```
OrganizeUniversity/
  docs/     методология, план, принятые решения
  engine/   движок расписания: чистая логика + тесты
  server/   сервер, база, Google, фоновые проверки
  web/      интерфейс
  data/     база SQLite и резервные копии (не попадает в git)
```

## Этапы

Размер: **S** — небольшой, **M** — средний, **L** — большой.

### Этап 0. Подготовка · S

1. git, структура папок, TypeScript, линтер, тесты, скрипты запуска.
2. **Google Cloud — делаешь ты** по моей пошаговой инструкции (~10 минут): проект, включённый Calendar API, экран согласия, OAuth-клиент с адресом возврата `http://localhost:<порт>/auth/google/callback`. Client ID и Secret кладём в файл `.env`.
   Приложение остаётся в режиме Testing, ты добавляешь себя в тестовые пользователи. Для рабочего режима Google требует публичный сайт с политикой конфиденциальности — у локального сервиса его нет. Цена: Google выдаёт доступ на 7 дней, поэтому раз в неделю сервис просит войти заново.
3. Принятые решения по стеку записываем в `docs/`.

**Результат:** пустой проект запускается, тесты проходят, ключи Google на месте.

### Этап 1. Движок расписания · L — самый большой

Вся методология в виде чистой логики. Каждый модуль — со своими тестами.

1. **Время и интервалы:** недели семестра, часовой пояс, пересечения интервалов, буферы.
2. **Модель данных движка:** дисциплины, настройки, занятость (список занятых интервалов), текущий план.
3. **Проверка правил:** все жёсткие ограничения методологии. Возвращает список нарушений человеческим языком. Ею пользуются все остальные модули.
4. **Свободные окна и кандидаты:** сетка с шагом 15 минут в окнах для учёбы, устойчивость каждого слота по неделям семестра.
5. **Бюджет:** расчёт частот (основные 3 → 2), бюджет недели в часах и долях.
6. **Ритм:** идеальные рисунки дней, штрафы за соседние дни и длинные перерывы.
7. **Построение каркаса:** основные → дополнительные, оценка слотов, локальное улучшение.
8. **Развёртка по неделям:** каркас превращается в занятия; конфликтующие переносятся с минимальным вмешательством и помечаются «перенесено: <событие>».
9. **Компромиссы:** перебор ослаблений по одному; в ответ — только варианты, которые решают проблему, с их ценой.
10. **Конфликт после построения:** до трёх вариантов переноса + «пропустить» / «оставить как есть»; повторяющееся событие → предложение перенести слот каркаса насовсем.
11. **Пропуски:** варианты переноса в пределах 7 дней с итоговой нагрузкой; разбор нескольких пропусков за раз.
12. **Изменения в середине семестра:** добавление и удаление дисциплины, расчёт «было → станет», перестройка только будущего.
13. **Ручной перенос:** проверка перетаскивания и правок из Google.
14. **Аналитика:** прогресс, посещаемость, серия, прогноз к концу семестра, калибровка длительности, факты для итогов семестра.

**Тестовые сценарии** (наборы искусственных календарей):

- свободная неделя;
- утро занято (твой пример);
- рваный календарь, каждая неделя разная;
- перегруз — не помещается даже минимум;
- добавление дисциплины на 5-й неделе;
- новое повторяющееся событие посреди семестра;
- серия пропусков подряд.

Плюс общая проверка: ни один результат движка не нарушает жёсткие правила.

**Результат и приёмка:** симулятор — команда, которая печатает расписание семестра таблицей по твоим реальным дисциплинам и ограничениям. Ты оцениваешь логику до того, как появится интерфейс.

### Этап 2. Данные и сервер · M

1. **База:** настройки, семестры, дисциплины, источники, слоты каркаса (с историей изменений), занятия, фактическое время, итоги и «с чего продолжить», очередь решений, контрольные точки.
2. **API:** дисциплины и источники; настройки; семестр (создать → черновик → подтвердить); расписание (неделя, семестр, ручной перенос); занятие; решения; статистика.
3. **Занятие как набор состояний:** не начато → идёт (фокус / перерыв) → пауза → завершено (полностью или досрочно) → ждёт итога → закрыто. Время считается по отметкам на сервере, поэтому перезагрузка страницы или закрытый браузер не сбивают таймер.
4. **Очередь «Решения»:** конфликты, пропуски, калибровка, контрольные точки — единый список вопросов к тебе.
5. **Фоновые проверки** при открытии и каждые 15 минут: пропуски, конфликты, наступление контрольных точек.
6. **Сохранность данных:** резервная копия базы раз в день (хранятся последние 14) и экспорт итогов занятий в Markdown / JSON.

**Результат:** вся логика доступна через API и покрыта тестами.

### Этап 3. Google Календарь · M

1. Вход через Google, хранение доступа локально, автоматическое продление. Когда доступ истекает (раз в 7 дней в режиме Testing) — заметная кнопка «Войти заново»; пока не вошёл, сервис работает с последними данными календаря.
2. Список твоих календарей и выбор, из каких брать занятость.
3. Чтение событий на весь семестр: учитываются только занятые — без «свободен» и отклонённых встреч.
4. Создание календаря «Мой университет»; запись, изменение и удаление занятий без напоминаний.
5. Синхронизация каждые 15 минут: новые события → конфликты в «Решениях»; твои правки занятий в Google → ручной перенос с проверкой правил.
6. Нет интернета → сервис работает с последними данными, синхронизируется позже и честно показывает «календарь не обновлялся с …».

Права доступа минимальные: чтение твоих календарей и запись только в «Мой университет».

**Результат:** черновик строится по настоящему календарю, занятия появляются в Google.

### Этап 4. Технический интерфейс и проверка логики · M

Простой интерфейс без дизайна, чтобы пройти руками все сценарии:

- мастер первой настройки;
- дисциплины и источники;
- семестр: создание → черновик → компромиссы → подтверждение;
- «Сегодня» и расписание недели;
- занятие: таймер Помодоро, пауза, досрочное завершение, итог, «с чего продолжить»;
- «Решения»;
- статистика и контрольные точки (пока таблицами).

**Приёмка:** ты проходишь сценарии сам. Предлагаю пожить с этим 3–5 дней на настоящем расписании — так ошибки логики всплывут до того, как мы вложимся в дизайн.

### Этап 5. Дизайн · L

1. **Дизайн-система:** палитра (белый, синий, фиолетовый), шрифты, отступы, компоненты.
2. **Макеты ключевых экранов** — на твоё утверждение до вёрстки.
3. **Экраны:**
   - Сегодня;
   - Расписание: неделя и семестр, перетаскивание занятий;
   - Дисциплины и карточка дисциплины: цель, метрики, источники, прогресс, «с чего продолжить»;
   - Экран занятия — режим погружения: таймер, звуки, источники под рукой;
   - Итог занятия;
   - Решения;
   - Статистика с графиками;
   - Контрольные точки и итоги семестра;
   - Настройки и мастер первой настройки.
4. **Звуки природы:** записи со свободной лицензией (дождь, лес, море, костёр, ручей и др.), микшер, громкость, пауза в перерывах.
5. **Детали:** мягкие анимации, состояния «пусто / загрузка / ошибка».

**Результат:** готовый интерфейс поверх проверенной логики.

### Этап 6. Запуск и полировка · S

1. Ярлык на рабочем столе: запускает сервер и открывает браузер. По желанию — автозапуск вместе с Windows.
2. Особые случаи: сон и пробуждение ПК во время занятия, закрытый браузер, смена часового пояса.
3. Финальный прогон всех сценариев и короткая инструкция.

## Точки приёмки с тобой

**Перед каждой точкой приёмки я сам проверяю результат** и только потом показываю тебе:

1. прогоняю линтер, проверку типов и все тесты;
2. запускаю то, что готово, и прохожу сценарии этапа руками;
3. сверяю результат с этим планом и с методологией — по пунктам;
4. если что-то расходится — исправляю и проверяю заново; что исправить не удалось — честно называю.

Точки:

1. После этапа 0 — ключи Google получены.
2. После этапа 1 — смотришь расписание по своим дисциплинам в симуляторе.
3. После этапа 4 — проходишь все сценарии в техническом интерфейсе.
4. На этапе 5 — утверждаешь макеты до вёрстки.
5. После этапа 6 — запуск.

## Не входит в первую версию

- Практические занятия по итогам (данные для них уже копятся).
- Разные буферы для разных типов событий.
- Телефон и доступ с других устройств.
- Напоминания.
